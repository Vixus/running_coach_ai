# Implementation Plan: Athlete Timezone Auto-Detection

**Branch**: `002-feature-athlete-timezone` | **Date**: 2026-04-04 | **Spec**: [spec.md](spec.md)  
**Input**: Feature specification from `/specs/002-feature-athlete-timezone/spec.md`

## Summary

Populate `athletes.timezone` automatically from GPS coordinates during onboarding and after each activity ingestion, then re-register the athlete's morning check-in cron job whenever the timezone changes. Remove the global 06:00–22:00 server-time activity polling gate so athletes in all timezones receive timely ingestion. No schema changes required; one new utility module (`timezone_utils.py`) added; three existing modules touched.

## Technical Context

**Language/Version**: Python 3.11  
**Primary Dependencies**: `timezonefinder>=6.0.0` (new), `APScheduler 3.x` (existing), `SQLAlchemy` (existing), `garminconnect`/`garth` (existing), `slack-bolt` (existing)  
**Storage**: SQLite via SQLAlchemy ORM — existing `athletes.timezone TEXT NULLABLE` column  
**Testing**: pytest — unit tests only (no new integration tests required for this feature)  
**Target Platform**: Linux server (Docker container, Synology NAS deployment)  
**Project Type**: Background service / daemon (Slack bot + APScheduler)  
**Performance Goals**: Timezone update must occur within the same activity-ingestion cycle (≤10 min after Garmin sync per SC-002); scheduler re-registration must be synchronous and non-blocking  
**Constraints**: No service restart permitted for timezone changes; `timezonefinder` must be instantiated once (thread-safe reads); GPS fallback must not issue additional Garmin API calls  
**Scale/Scope**: Small cohort (~2–10 athletes); timing correctness is the primary concern, not throughput

### Key Design Decisions

**`timezone_utils.py`**  
Module-level `TimezoneFinder` singleton, lazily initialised on first call. Thread-safe (reads only; no mutation after init). Exposed as a single function `derive_timezone_from_coords(lat, lon) -> str | None`.

**Hybrid onboarding path**  
`_complete_onboarding` keeps the hardcoded city table as primary. When a city is NOT in the table but `home_lat`/`home_lon` are available (e.g., from a future geocoder), `derive_timezone_from_coords` is called. Fallback to `"UTC"` only if both paths fail. This avoids breaking existing onboarding behaviour for supported cities.

**Timezone update placement in ingestion pipeline**  
`_ingest_and_feedback` calls `extract_activity_start_coords(detail)` and `derive_timezone_from_coords` after `generate_post_run_feedback`. The `scheduler` object is passed down from `_run_activity_poll` → `_ingest_and_feedback` as a new positional argument. This avoids a global reference while keeping code testable.

**24/7 polling**  
The two lines `if not (6 <= now.hour < 22): return` are removed from `_run_activity_poll`. The 16-hour stale-window guard inside `_ingest_and_feedback` remains as the sole backstop.
